## Performance inputs and order

The unchanged S6 contact fixture is authoritative: WorldId (6,6), seed 42, 512/2,048 adult Nurses, dense/dispersed layouts, original per-ant reserves and social configuration, 10 simulated seconds in ten 1 s advances. Correction flags remain disabled as in the original performance fixture. Keep actual contacts, collision checks, decisions, transactions, RNG and every event. Include a 128-worker smoke/parity check, without mixing it into the primary scaling estimator.

Primary uninstrumented Release: **three sessions**, each with **12 four-run blocks per layout**. A=512, B=2,048. Odd blocks are ABBA, even blocks BAAB. Alternate the dense/dispersed block order, reversing its first layout in the second session. Each session starts with one explicitly labeled warmup block per layout; retain those rows but exclude them from the prespecified acceptance estimators. Each measured size/layout therefore has 24 samples/session, 72 pooled; **288 measured rows**, plus 24 warmups. Never remove a slow, hot, busy or failed sample; annotate it. Leave a fixed 250 ms between individual runs and a fixed 5 s between sessions. Do not execute local builds, tests, ecological experiments or other agent workloads during timing.

Run the same native executable and fixture in one process per session, with a fresh world for each sample. Record executable/source/toolchain/configuration hashes, all argument/input/order records, process ID, process/thread CPU time and cycle counts where available, and UTC/monotonic phase boundaries. Setup, simulation advance, checkpoint encode and restore are independently timed. Destruction, telemetry, validation and file output remain outside those four timers. Record memory/current and peak RSS, checkpoint size, event/queue counts, candidates, buckets, tree visits and exact state/trace hashes. Verify restored checkpoints and a further 1 s continuation against an un-restored world outside timing.

Use one logical CPU from the highest OS-reported performance efficiency class, choosing the lowest logical index in that class before timing. Record topology and affinity; do not assume even/odd indices mean P/E cores. Pin the observer process to other logical CPUs where supported. Keep Normal priority, the existing power plan and AC/battery state; do not silently change global power policy, disable services or install kernel drivers. A nonmatching affinity or changed power state is a validity limitation, not grounds to discard a sample. Record before/after snapshots and all transitions detected by telemetry.

Additional fixed controls, outside the primary estimators:

- Four ABBA/BAAB blocks per layout with telemetry disabled, same affinity/binary, to quantify observer overhead. Their outcomes cannot replace the primary matrix.
- Four dense 2,048-worker blocks comparing exhaustive/bounded policies in alternating ABBA/BAAB order (16 rows). Report the original >=4x matched speedup gate and retain exact counts for each policy. Do not demand identical decision outcomes between different policies.
- Profiling-on attribution: four primary size blocks per layout (32 rows), with the same affinity and telemetry. The nine existing scopes cover index maintenance, sampling, spatial validation, scheduling, transaction/journal, fact append, physiology, policy and residual. Record inclusive/exclusive nanoseconds and calls separately for all four phases. Require per-sample exclusive accounting and hash/work parity with normal builds. Instrumented latency never substitutes for acceptance latency. If a code optimization is justified, repeat these controls and the complete primary matrix on the corrected binary; retain both.

## Telemetry and uncertainty

Use monotonic/UTC-aligned samples at a target 100 ms interval for OS-reported per-core frequency/performance counters, system and selected-core busy time, memory, power-source/battery-saver status and benchmark CPU activity. Record actual sample times, status/error codes and collection duration; short phases may have only bracketing samples. Sample process CPU load by PID at session boundaries and report system load during runs; do not collect command lines, credentials or unrelated file contents. Power-plan GUID and hardware/OS/topology/toolchain information are part of provenance. OS frequency estimates are not a direct hardware frequency measurement.

Probe available CPU temperature/package-power sensor providers. Record real sensor names, units, timestamps and values if available. An ACPI thermal zone is not automatically CPU package temperature. The initial Windows preflight has no accessible ACPI CPU temperature or Libre/OpenHardwareMonitor service. If an existing user-provided source is available before timing, record and correlate it; otherwise fields remain explicitly unavailable, with provider errors. No fabricated temperature, zero substitution, unreviewed driver installation or claim to have excluded thermal throttling. Missing thermal/package-power data limits causal explanations and an unconditional hardware-validation conclusion, even if controlled latency meets its numeric gate.

Report raw sample p50/p95/p99/max by phase, layout, size and session. Tails from 24/72 samples are descriptive, not a production tail guarantee. For each balanced block compute mean(B advance)/mean(A advance), preserving local pairing. Report its median, geometric mean and 95% hierarchical percentile-bootstrap interval: resample the three sessions and then their 12 blocks, 4,096 resamples, analysis seed 6206. Also report the original ratio of p50(2,048)/p50(512), per session and pooled. CPU-time/cycle ratios and telemetry correlations are explanatory diagnostics, not replacements for wall time.

Keep the **<=6x** dense growth threshold. Report the original p50 gate independently. A robust controlled-host conclusion additionally requires all three session p50 ratios <=6, the paired-growth interval upper bound <=6 and largest/smallest session p50 ratio <=1.25. These are declared uncertainty checks, not an increased threshold. Keep <=16 examined candidates and the >=4x matched exhaustive speedup gate. If stability/telemetry or latency gates fail, distinguish numeric failure from insufficient measurement certainty. Propose reviewed follow-up or later layered simulation budgets; do not implement LOD or silently adopt a different threshold. No indefinite retuning/rebenchmarking until a favorable result.

## Scarcity diagnosis

Use every seed **1..16**, worker counts **8/32/128**, source protein **500/2,000 ug**, `legacy`/`combined`, unchanged unmirrored integrated fixture, 180 s: **192 replay cases**. The 2,000 ug and 32-worker cells are controls, not substitute endpoints. Reconcile each trace/state with its original S6.1 case. Retain all four original ablation arms in archival analysis. Do not select a representative favorable seed.

Reconstruct actual protein transfers for every seeded brood identity: donor, recipient, event/time, amount, cumulative intake, retained crop/tissue, threshold attainment, emergence and death. Reconcile every introduction, available/depot/cargo/adult/brood/dead store; protein transfer is not new input. Measure distribution concentration, fully/partially/unfed brood, time to the unchanged 100 ug fixture requirement and time remaining for development. An initially supplied pupa is not a success caused by a new gift. Separate partial provision from completion, and avoid declaring a spreading-versus-completion tradeoff biologically optimal.

At actual nursing decisions, observe the committed local sample, reachable eligible recipients, compatible protein, selected action and local conditions; distinguish no nursing, refill precedence, self-maintenance, a missed eligible contact, filled crop, proposal competition and depleted compatible supply at resolution. Observer-only exhaustive comparisons cannot become worker information. Export proposal/resolution evidence and classify failures only as far as the actual trace supports. Respect life-stage/phase order and same-time competition; an end-of-timestamp observation is not automatically the earlier proposal state. Verify instrumentation does not change canonical facts.

Compare all paired seeds for actual protein delivered, donor retention, unmet demand exposure, failed/partial/successful gifts, contact opportunities and program changes. Use 4,096 paired-seed bootstrap resamples, seed 6206. Evaluate whether contact scarcity and ordinary uniform local choice explain the dense case, or whether there is an implementation bias. A separate equal-local-demand diagnostic uses **64 seeds**, **16 equal larvae**, a fixed donor, and four label/spatial permutations; record every choice and inclusion count. Permuting labels cannot provide a food oracle or force the desired recipient. Distributional differences are evidence with uncertainty, not a requirement for exact per-seed relabeling equivalence.

If a concrete model defect is found, document its counterexample before coding, keep it opt-in where semantics change, and run the same 192 controls plus all relevant archived integration and restore tests. Otherwise preserve the negative results as a qualified engineering allocation tradeoff and/or unresolved limitation. No global optimizer, forced completion, hidden food, default tuning or guarantee of increased emergence.
